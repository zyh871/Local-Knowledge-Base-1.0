## 一、现状诊断（只列真正卡住用户的地方）

| 现象 | 原因（代码位置） | 影响 |
|---|---|---|
| 交付物点不开、下不来 | `downloadRunFile()` 走 `a[download]`，WebView2 没接 `DownloadStarting` | 用户只能去下载目录翻 |
| **步骤失败后整个任务卡死** | `runnable_next_step` 遇到 `failed` 返回 `None` → `next_runnable_idx` 为 null | 「继续执行」按钮消失，用户不知道该怎么办 |
| 成本事后才知道 | `_usage_summary()` 只在最后汇总 | 看到 46.3k tokens 时钱已经花了 |
| 一次任务 7 次模型调用 | 每步独立调用（交付物不计，见 P3） | 属于必要成本，但缺上限 |

## 二、已落地项

### P1 交付物「应用内可读」✅

**改动**
- 后端：`GET /workflow/files/{id}/preview`（文本，2 MB 截断）与 `/preview/raw`（图片 inline）。
- 前端：`components/workflow/ArtifactDrawer.vue` 右侧抽屉，左列表右预览，Markdown 直接渲染。
- 入口：交付物卡片「浏览全部」+ 产物行点文件名；下载优先原生「另存为」，浏览器退回 blob。

**收益**：不再依赖浏览器；看完即下载。

---

### P3 交付物「确定性拼装」✅（原本就实现了）

`deliver_run()` 调 `build_deliverable()`，**完全不调 LLM**：

```python
# app/workflow/delivery.py 开头的原话
# 确定性 → 同样输入永远同样输出，可以单测
# 不花钱、不耗时、不会失败
```

所以「本任务 7 次模型调用」里**不包含交付物生成**。这一条在上一版方案里被误写成「待做」，
实际核对代码后确认早已实现，无需改动。教训：写方案前先读实现，别照着想象提需求。

---

### P5 失败可续跑 ✅

**问题**：`runnable_next_step()` 里 `failed` 落到 `return None`（注释还写着 `failed` 在里面），
导致 `next_runnable_idx = null` → 前端「执行下一步 / 自动执行剩余」全部 disabled。
用户唯一的出路是手动点失败步骤上的「重试」，而多数人不知道要去找它。

**改动**
- `app/workflow/executor.py`：`failed` 视为可执行，原地重试。
- `app/services/workflow_service.py`：`_EXECUTABLE_STEP_STATUSES` 加 `failed`。
- 前端 `StepTimeline`：下一步是失败步时，按钮变「重试第 N 步」/「从失败处继续」，
  tooltip 说明「后面的步骤会接着跑」。

**没改的**：`rejected` 仍然不能自动跑（用户明确拒绝的东西不该被偷偷重跑）。

**已有基础**：LLM 步骤本来就有「流式失败 → 回退同步调用」的一次重试，覆盖网络抖动。

**收益**：失败不再让任务变成死胡同；重试只花一步的钱，而不是整轮。

---

### P6 token 预算 ✅

**改动**
- `WORKFLOW_MAX_TOKENS_PER_RUN`（默认 120000，0 = 不限制）。
- `stream_execute_step` 在**锁内、执行前**用已落库的 usage 累计判断，超限直接返回：

```json
{"ok": false, "code": "budget_exceeded",
 "error": "本任务已用 121,033 tokens，达到上限 120,000。可调高 ... 后继续，或直接生成交付物。"}
```

- 判定抽成 `budget_exceeded(used, limit)`，单测覆盖「恰好等于上限也要停」。

**刻意不做的事**：超限时**不把 run 标成 failed**。这是暂停，不是失败——
用户可能只是想调高预算继续，或者现在就把已有产出打包带走。

## 三、未做项及原因

### P2 无依赖步骤并行 ⏸

方案原本估「耗时 -25~40%」。核对代码后发现前提不成立：

1. **没有依赖信息**。`steps` 表只有 `idx`，步骤之间靠「顺序」隐含依赖；`plan` 也不产出依赖关系。
   在这种情况下并行，第 3 步会读不到第 2 步的产出 —— 结果是**更快但更差**，不是优化。
2. 真要做得先加 `depends_on`（`PRAGMA` + `ALTER` 迁移）、改 `plan` 提示词让模型标注依赖、
   新增批量执行接口、处理并发写 SQLite 的锁竞争、前端改多步并发调度。
3. 而且现实收益有限：典型 7 步里只有 1–2 步是独立的工具调用，其余都是「基于上文写作」的串行链。

**结论**：这一轮不做。若要做，先做第一步——让 `plan` 输出 `depends_on`，其余不动，观察一周数据再决定。

### P4 模型分级 ⏸

需要先回答产品问题：哪两档？谁来配？用户只有一个月之暗面/智谱 key 时怎么降级？
在这些没定之前写代码，只会得到一个没人敢开的开关。

## 四、与其它改进的协同

```
P1 交付物抽屉  ←→  P6 预算：超限暂停后，用户可以直接生成交付物把已有产出带走
P5 失败续跑    ←→  P1：失败步骤的产出（部分内容）也能在抽屉里看到，不必重跑才能确认
P6 预算        ←→  步骤卡上的 token 汇总：两者用同一份 _usage_summary，数字不会对不上
```

## 五、验收方式

| 项 | 怎么验 |
|---|---|
| P1 | 工作页 → 交付物「浏览全部」→ 左侧两个文件、右侧 Markdown 渲染 |
| P5 | 把 `WORKFLOW_MAX_TOKENS_PER_RUN=1` 后执行一步 → 报 budget_exceeded；改回后按钮恢复 |
| P6 | 同上；或单测 `tests/unit/test_workflow_budget.py` |
| P3 | `deliver_run` 的日志里没有 LLM 调用；单测 `test_workflow_delivery*` |

## 六、不建议现在做的

- **多 Agent 编排**：单链路已跑通，拆多 Agent 只会增加状态同步成本。
- **把交付物写进向量库**：会让对话检索命中工作流中间稿，属于噪音（现有设计刻意隔离，应保持）。
