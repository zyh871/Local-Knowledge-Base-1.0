开发者文档

智鲸 AI 是一个可本地部署的知识库问答系统：文档解析与混合检索、LangGraph 问答编排、 带人工审批的工作流引擎、AI 创作，以及把整套前后端打包成桌面客户端的构建链。 这里说明它由什么组成、怎么跑起来、怎么改。

快速开始 在 GitHub 上查看
Python 3.10+ / Node 18+ FastAPI · Vue 3 · LangGraph 本地优先，数据不出本机

项目介绍

智鲸 AI 把「问自己的文档」做成一个能装在本机的软件：导入资料 → 提问 → 得到带出处的回答， 同时提供工作流编排与 AI 创作。后端一套代码既能作为 Web 服务部署，也能被桌面客户端内嵌托管。

三条主线

知识库问答

BM25 关键词 + 向量语义双路召回，RRF 融合排序；回答里带编号引用，可点回原文。

工作流

澄清 → 计划 → 审批 → 执行 → 交付。步骤落在数据库里，长任务中断后能接着跑。

AI 创作

文生图 / 图生图 / 文生视频，多供应商可切换，产物落盘到本地资产库。

设计取向

  • 本地优先：知识库原文、对话记录、生成物默认只写本机；只有被检索命中的片段会随请求发给模型端点。
  • 可换模型：智谱、百炼、ModelScope、本地 Ollama、任意 OpenAI 兼容端点，改 MODEL_BACKEND 即可。
  • 可解释：回答必须给出处；工作流每一步都要能追问「为什么这么做」。
仓库： github.com/zyh871/Local-Knowledge-Base-1.0 —— 问题反馈与功能建议请走 Issues，改动请走 Pull Request。

技术栈

层选型说明
前端Vue 3 + Vite + Vue Router单页应用，主题用 CSS 变量驱动，不依赖 UI 框架
后端FastAPI + Pydantic SettingsSSE 流式输出；配置分组统一 env_prefix
编排LangGraph问答状态图 + 工作流状态图；工作流用 HTTP 显式状态机，不依赖 interrupt()
检索Chroma + BM25 + RRF向量库本地持久化，关键词索引单独保存，融合后统一排序
存储SQLite + Redis会话/画像/工作流/身份/团队/社区各一个库；Redis 仅作缓存，不可用时降级为进程内实现
模型智谱 · 百炼 · ModelScope · Ollama对话与嵌入分开配置，可分别指向不同服务
文档解析pypdf · python-docx · openpyxl · TesseractPDF / Word / Excel / PPT / 图片 OCR / 纯文本与代码文件
打包PyInstaller + IExpress图形安装器；桌面快捷方式用 WScript.Shell 生成真 .lnk

目录结构

Local-Knowledge-Base/
├─ backend/                 FastAPI 服务
│  ├─ app/api/v1/           路由层（只做参数校验与依赖装配）
│  ├─ app/services/         业务层（会话、文档、工作流、创作）
│  ├─ app/graph/            LangGraph 问答图与工作流图
│  ├─ app/rag/              检索、嵌入、模型供应商、生成
│  ├─ app/repositories/     SQLite 仓储
│  ├─ app/core/             配置、日志、Redis、异常
│  └─ tests/                单元 + 契约测试
├─ frontend/                Vue 3 前端
│  ├─ src/views/            对话 / 工作流 / 创作 / 模型广场
│  ├─ src/components/       侧栏、工作流组件
│  └─ scripts/              截图与端到端验证脚本
├─ landing/                 产品介绍页与打包脚本
├─ tools/                   本地模型检测、打包辅助
└─ docs/                    设计文档

依赖方向是单向的：api → services → graph/repositories → rag/tools → core。 tests/unit/test_layering.py 会用 AST 静态检查，反向引用会直接让测试失败。

使用说明

1. 准备环境

  • Python 3.10+（开发环境用 3.13 验证）
  • Node.js 18+ 与 npm
  • 可选：Redis（不装会降级为进程内缓存，仅建议开发用）

2. 启动后端

cd backend
python -m venv venv
# Windows
venv\Scripts\activate
# macOS / Linux
source venv/bin/activate

pip install -r requirements.txt

在 backend/.env 里至少配好这几项（缺管理员账号会在启动时报 ValidationError）：

ADMIN_USERNAME=admin
ADMIN_PASSWORD=换成你自己的密码
JWT_SECRET_KEY=用 python -c "import secrets;print(secrets.token_hex(32))" 生成

# 用本地模型（需要先装 Ollama）
MODEL_BACKEND=ollama
LLM_MODEL=qwen2.5:7b
EMBEDDING_MODEL=local-tfidf

# 或者用云端模型
# MODEL_BACKEND=zhipu
# ZHIPU_API_KEY=你的密钥
# 启动（Windows 下不要用 uvicorn.exe，中文路径会乱码）
python -m uvicorn app.main:app --reload --port 8000

3. 启动前端

cd frontend
npm install
npm run dev        # 默认 5173，/api 反向代理到 8000

4. 不想配模型？先自检

仓库里带了一个只依赖标准库的检测程序，会依次检查 Ollama 是否安装、服务是否在跑、有没有可对话的模型：

python tools/ollama_bootstrap.py            # 自检并给出指引
python tools/ollama_bootstrap.py --chat     # 直接用本地模型对话
python tools/ollama_bootstrap.py --write-env  # 写好 backend/.env
python tools/ollama_bootstrap.py --serve    # 用本地模型起整套服务
嵌入模型单独配置。检索用的 EMBEDDING_MODEL 与对话模型无关； 若没有可用的向量模型，直接写 local-tfidf（纯本地、零下载）。 换过嵌入模型必须重建向量库：POST /rebuild-vectorstore， 否则会报维度不匹配。

5. 常见操作

操作入口
导入文档对话页输入框左侧「上传文件」，或 POST /upload-multiple
加自定义模型模型广场 → 最后一张「自定义模型」卡片，填 Base URL / 模型 ID / 密钥
建工作流侧栏「工作流」，描述目标后由模型先出计划，人工审批再执行
跑测试pytest --basetemp=./_pytmp（Windows 沙箱下必须指定临时目录）
打包客户端python landing/deploy/build_client.py

关键配置项

变量作用
MODEL_BACKENDzhipu / ollama / openai 等，决定对话与嵌入走哪家
LLM_MODEL对话模型名；非法值会 400，不会静默回退
EMBEDDING_MODEL检索用嵌入模型；无可用模型时写 local-tfidf
OLLAMA_BASE_URL本地 Ollama 地址，默认 http://127.0.0.1:11434
ADMIN_USERNAME / ADMIN_PASSWORD初始管理员，必填，缺了启动即失败
ALLOW_CUSTOM_MODELS是否允许在界面上接自定义端点
WORKFLOW_FS_BROWSE工作流是否允许读写本机目录（默认开，多用户部署需评估）
SERVE_FRONTEND_DIR设置后由后端同源托管已构建的前端（桌面客户端用）

新增配置分组时必须声明 env_prefix（pydantic-settings 不会按类名推导）， 并在 tests/unit/test_config.py 补一条绑定测试。

接口约定

  • /ask 的参数校验失败返回 400 且带 answer 字段，不是 422。
  • 流式输出的事件顺序固定：intent → sources → (tool_calls) → chunk* → final，每次请求恰好一个 intent。
  • 问答接口的入参是 model，出参是 used_model / truncated。
  • 工作流是显式状态机：plan 与 execute 是两个独立入口，各自跑到结束；状态推进必须单调。

改动端点后请跑 tests/test_openapi_contract.py，并同步 tests/data/openapi_v3_baseline.json。

贡献指南

提交流程

  1. Fork 仓库并从 main 拉分支：feat/xxx、fix/xxx、docs/xxx。
  2. 小步提交，一个提交只做一件事；提交信息用中文或英文都可以，但要能说清「改了什么、为什么」。
  3. 提 PR 时写清：现象 / 原因 / 改动点 / 怎么验证的（截图或命令输出）。
  4. 涉及界面的改动请附桌面与移动端截图；涉及接口的改动请说明兼容性。

代码规范

  • 遵守分层：不许让 core 反向依赖上层，rag 不许 import graph；test_layering.py 会拦。
  • 新增 WorkflowState 字段必须写进 app/graph/workflow/state.py，否则 LangGraph 会静默丢弃。
  • SQLite 加列必须 PRAGMA table_info 判断后 ALTER，CREATE TABLE IF NOT EXISTS 不会补列。
  • 前端纵向滚动区记得配 min-h-0；defineEmits 的返回值要赋值，否则按钮会静默失效。

提交前自检

cd backend
pytest --basetemp=./_pytmp          # 全量测试
pytest tests/unit/test_layering.py  # 分层约束

cd ../frontend
npm run build                        # 必须能构建通过

不要提交的内容

  • backend/.env、任何密钥与令牌
  • data/*.db、chroma_db/、logs/ 等运行时数据
  • node_modules/、dist/、构建中间产物
第一次贡献不知道从哪下手？先看 Issue 里带 good first issue 标签的条目， 或者在 Discussions 里说明你的使用场景。
